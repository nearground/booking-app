# Spanish localization

## Outcome and MVP traceability

Customers can use the agreed public booking experience in Spanish with consistent language across UI states, errors and checkout.

## Scope and non-goals

Introduce frontend i18n architecture in the Vite app. App is a Vite React SPA (`frontend/src/main.jsx`, `frontend/package.json`) with embedded UI strings; no i18n package/config was found. The booking app stays on Vite (Docusaurus scope was narrowed to internal docs), so i18n targets the Vite app only. Initial recommended scope is customer-facing booking and organization pages; admin/organizer panels and emails require decisions; internal Docusaurus docs are out of scope. Include locale fallback, pluralization and date/number formatting; avoid copy-only translation without locale behavior.

Decision (user, 2026-10-26): missing Spanish strings are initially generated by a translator API for efficiency, and machine translation is also a feature of the backend API itself. Scope therefore includes:

- A backend translation service behind a provider-agnostic interface, using a self-hosted **LibreTranslate** container added to the development Compose stack (no API key or third-party data sharing), with caching of results so each source string is translated once.
- A catalog tool/script that fills missing `es-MX` UI keys through that service, marks them as machine-translated, and leaves human-reviewed keys untouched.
- An API capability to return translated content when no human translation exists, covering organizer content (experience, organization) **and user comments**, labelled as machine-translated in the UI with a "show original" toggle.

## Acceptance criteria

- [ ] EN | ES switcher is in the top menu on all device sizes; with no explicit choice the browser locale decides, an explicit choice persists in a cookie; missing translations fall back consistently.
- [ ] Reviewed Spanish translations cover all visible strings in approved scope: navigation, details, sessions/dates, cart, checkout, receipt, validation, empty/error states and org landing pages.
- [ ] Dates, numbers, currency presentation and plurals use locale without altering server prices/timezone semantics.
- [ ] Tests cover selection/persistence, fallback, representative customer booking and missing-key checks.
- [ ] Missing `es` catalog keys can be filled via the translator service; machine-translated keys are flagged and never overwrite reviewed ones.
- [ ] Backend translation endpoint/service caches results, is rate-limited, works with a stub provider in tests and degrades to the source language if the provider fails.

## Branch independence and ownership

- Baseline: `main`. All Epic branches are created from the same `main` commit.
- Owned paths: `frontend/src/**` i18n bootstrap/resources and approved public components; backend translation service/route/cache model and its migration; LibreTranslate service in `docker-compose.yml`; catalog fill script; tests.
- Shared files/contracts and owner: This Epic owns locale selection, catalog conventions and formatting policy. Integrate after feature UI edits because strings share those files.
- Parallel-ready assessment: Not parallel-ready for broad rollout: overlaps feature-owned UI files. The i18n bootstrap and the backend translation service can be built early; schedule string extraction after listed customer UI Epics.

## Risks, assumptions and open questions

- Spanish for customer pages only or also admin and emails? Recommendation: public customer flows first.
- Decided: locale `es-MX` (MXN-aware currency/date formats), LibreTranslate self-hosted, comments included in machine translation.
- Decided: an EN | ES switcher in the top menu (`GlobalNavbar`). Persistence follows the user's selection mode: "Auto" uses the browser locale (`navigator.languages`) with nothing stored; an explicit EN/ES choice is stored in a cookie (readable by the backend for API translations and emails). Logged-in profile storage is not required.
- Machine translations are acceptable initially; human review can happen later.
- Risk: LibreTranslate quality for es-MX is below commercial providers, and its container needs ~2 GB RAM plus model download on first start; keep the provider interface swappable.
- Risk: translating comments on demand can be costly; translate lazily on first Spanish view and cache, invalidating when a comment is edited.
- Assumption: server error codes remain stable; frontend maps errors to translated copy.
